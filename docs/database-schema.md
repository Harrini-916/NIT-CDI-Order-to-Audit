# Database Schema

## 1. Document status

This file is the source of truth for the database design.

`docs/database-design.md` explains the design. `docs/er-diagram.md` shows the entities and relationships. If those files disagree with this one, this file wins.

PostgreSQL is the target engine. No SQL has been written yet, and no table in this document has been created.

Database name: `nit_cdi_order_audit`

The internship scope is unchanged: authentication and roles, sales orders, inventory, BOM and production, GST billing, product costing, and reports with an audit trail.

## 2. Conventions

These conventions apply to every table.

| Rule | Decision |
|---|---|
| Primary key | `BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| Required foreign key | `NOT NULL`, `ON DELETE RESTRICT`, `ON UPDATE RESTRICT` |
| Money on invoices and payments | `DECIMAL(12,2)`, tax-exclusive taxable values |
| Material unit cost | `DECIMAL(14,4)`, so a weighted average can keep fractional paise |
| Material and movement value | `DECIMAL(14,2)` |
| Raw-material quantity | `DECIMAL(12,3)`, always greater than zero on documents and movements |
| Finished-goods quantity | `INTEGER` count of packets, greater than zero on documents and movements |
| Stock balance | Greater than or equal to zero. The posting transaction rejects a balance that would go negative |
| Date and time | `TIMESTAMPTZ` for moments in time. `DATE` only for a business date such as invoice date |
| Editable documents | `row_version INTEGER NOT NULL DEFAULT 1`. Each successful update increments it |
| Posted history | Invoices, payments, stock movements, posted production runs, locked BOMs, and audit logs are append-only |

Column checks cover one row. Rules that compare two tables are enforced in the posting transaction and, when SQL is written, by deferred constraint triggers. Those cross-table rules are listed under each area below.

### Table: production_material_usage

| Column | Data Type | Constraint |
|---|---|---|
| usage_id | BIGINT | Primary key, identity |
| production_run_id | BIGINT | NOT NULL, FK → production_runs.production_run_id, ON DELETE RESTRICT |
| bom_item_id | BIGINT | NOT NULL, FK → bom_items.bom_item_id, ON DELETE RESTRICT |
| material_id | BIGINT | NOT NULL, FK → raw_materials.material_id, ON DELETE RESTRICT |

| total_cost | DECIMAL(14,2) | NULL, CHECK IS NULL OR >= 0 |

UNIQUE (`production_run_id`, `bom_item_id`).

UNIQUE (`production_run_id`, `material_id`).

`material_id` must match `bom_items.material_id`, and that BOM item must belong to the run's BOM.

Planned usage is snapshotted when the run is created:

`planned_quantity = ROUND(bom_items.planned_quantity * production_runs.planned_quantity / bom_headers.planned_output_quantity, 3)`

`actual_quantity`, `unit_cost`, and `total_cost` are filled when material is issued. `unit_cost` is the weighted-average cost at that moment. `total_cost = ROUND(actual_quantity * unit_cost, 2)`.

### Calculated production results

These values are calculated from the stored quantities and costs. They are not stored columns.

| Result | Formula | When it exists |
|---|---|---|
| Yield percent | `good_quantity / planned_quantity * 100` | Run is completed or posted |
| Yield variance | `good_quantity - planned_quantity` | Run is completed or posted |
| Unexplained loss | `planned_quantity - good_quantity - damaged_quantity` | Run is completed or posted |
| Material variance | `actual_quantity - planned_quantity` | That usage line has an actual quantity |
| Cost per good packet | `SUM(usage.total_cost) / good_quantity` | Run is posted and `good_quantity` > 0 |

A positive material variance means more material was consumed than the BOM allowed. A negative yield variance means good output was below the planned packet count. Unexplained loss is the planned packets that are neither good nor damaged. It can be negative when good plus damaged output exceeds the plan.

When `good_quantity` is zero, finished goods are not received and cost per good packet is not calculated. The issued material cost remains on the usage lines.

Example: BOM output is 100 packets and uses 5.000 kg. A run plans 250 packets, so planned usage is 12.500 kg. Actual usage is 13.000 kg. Good output is 240 and damaged output is 6. Yield is 96 percent. Yield variance is -10 packets. Unexplained loss is 4 packets. Material variance is 0.500 kg. If issued material cost is 1200.00, cost per good packet is 5.00.

## 10. Inventory

Stock documents and the ledger are separate. Purchases, production, and dispatches say what should happen. Movement rows are the history. Balance rows are the locked current position and must be updated in the same transaction as the movement.

Every movement quantity is positive. `direction` says whether stock increases or decreases.

### Table: raw_material_balances

| Column | Data Type | Constraint |
|---|---|---|
| material_id | BIGINT | Primary key, FK → raw_materials.material_id, ON DELETE RESTRICT |
| quantity_on_hand | DECIMAL(12,3) | NOT NULL, CHECK >= 0 |
| total_value | DECIMAL(14,2) | NOT NULL, CHECK >= 0 |
| average_unit_cost | DECIMAL(14,4) | NOT NULL, CHECK >= 0 |
| updated_at | TIMESTAMPTZ | NOT NULL |

`average_unit_cost` is zero when quantity is zero. Otherwise `total_value / quantity_on_hand` matches the stored average after rounding to four decimal places.

Raw material is not reserved when a production run is only planned. The issue transaction locks this row and fails when quantity is insufficient.

### Table: finished_goods_balances

|---|---|---|
| product_id | BIGINT | Primary key, FK → products.product_id, ON DELETE RESTRICT |

### Weighted average

The costing method on `company_profile` is weighted average.

- A receipt adds its quantity and value, then recalculates `average_unit_cost`.
- An issue uses the current average. Its `total_cost` is `ROUND(quantity * average_unit_cost, 2)`.
- A reversal puts back, or takes away, the original movement value.
- The posting transaction locks the balance row with `SELECT FOR UPDATE` before it reads the average.

After every posting transaction, quantity on hand equals inbound quantity minus outbound quantity, and total value equals inbound value minus outbound value.

## 11. GST invoices

One order has one invoice. Partial delivery is recorded as more than one dispatch against that invoice.

`unit_price` is tax-exclusive. Line taxable value is `ROUND(quantity * unit_price, 2)`.

Line GST is `ROUND(taxable_amount * gst_rate / 100, 2)`, half up to one paise.

Intra-state supply, including a union territory with the same state code, splits that tax. CGST is `ROUND(line_gst / 2, 2)` and SGST, or UT-GST, is `line_gst - cgst`, so the halves always add up to the line tax. IGST is zero.

Inter-state supply assigns the full line tax to IGST. CGST and SGST are zero.

Header tax and total are the sums of the posted lines. A deferred constraint at implementation time must reject a header that does not match its lines.

Example, intra-state, GST 18 percent, taxable value 10.05: line tax is 1.81, CGST is 0.91, SGST is 0.90, IGST is 0.00, line total is 11.86.

Example, inter-state, same taxable value and rate: IGST is 1.81, CGST is 0.00, SGST is 0.00, line total is 11.86.

| cancelled_by | BIGINT | NULL, FK → users.user_id, ON DELETE RESTRICT |
| cancelled_at | TIMESTAMPTZ | NULL |
| cancellation_reason | TEXT | NULL |
| row_version | INTEGER | NOT NULL, default 1 |
| created_at | TIMESTAMPTZ | NOT NULL |
| updated_at | TIMESTAMPTZ | NOT NULL |

Row checks:

- Intra-state: `igst_amount = 0`, `cgst_amount = sgst_amount`, and `total_amount = taxable_amount + cgst_amount + sgst_amount`.
- Inter-state: `cgst_amount = 0`, `sgst_amount = 0`, and `total_amount = taxable_amount + igst_amount`.
- Intra-state requires `company_state_code = customer_state_code`. Inter-state requires the codes to differ.
- `place_of_supply_state_id` is the customer state copied at posting. For goods, that is the place of supply.
- A posted or cancelled invoice has `invoice_number`, `financial_year`, `posted_by`, and `posted_at`.
- A cancelled invoice has `cancelled_by`, `cancelled_at`, and `cancellation_reason`.

Draft invoices have no invoice number. Posting copies company and customer identity, assigns the number, and freezes amounts. Posted amounts, lines, and party snapshots cannot be updated.

Cancellation is allowed only when the invoice is posted, every dispatch is still draft or already reversed, and the net payment is zero. Cancellation changes status and records the reason. It does not change amounts or reuse the number.

| Column | Data Type | Constraint |

UNIQUE (`invoice_id`, `order_item_id`).

Row checks:

- `taxable_amount = ROUND(quantity * unit_price, 2)`.
- `gst_amount = cgst_amount + sgst_amount + igst_amount`.
- `total_amount = taxable_amount + gst_amount`.
- Intra-state lines follow the header: IGST rate and amount are zero, and each of CGST and SGST is half of `gst_rate`.
- Inter-state lines follow the header: CGST and SGST rates and amounts are zero, and `igst_rate = gst_rate`.

Cross-table rules at posting:

- `product_id` matches the order item.
- The order item belongs to `invoices.order_id`.
- Invoice quantity is less than or equal to the order quantity.
- `hsn_code` and `gst_rate` are copied from the product at posting.

## 13. Payments

Outstanding amount is `invoices.total_amount - net receipts`. Net receipts are receipt amounts minus reversal amounts. The balance is calculated, not stored.

### Table: payments

| Column | Data Type | Constraint |
|---|---|---|
| payment_id | BIGINT | Primary key, identity |
| invoice_id | BIGINT | NOT NULL, FK → invoices.invoice_id, ON DELETE RESTRICT |
| entry_type | VARCHAR(20) | NOT NULL, CHECK IN (`receipt`, `reversal`) |
| amount | DECIMAL(12,2) | NOT NULL, CHECK > 0 |
| payment_date | DATE | NOT NULL |
| payment_method | VARCHAR(30) | NOT NULL, CHECK IN (`cash`, `upi`, `bank_transfer`, `cheque`) |
| reference_number | VARCHAR(100) | Optional |
| received_by | BIGINT | NOT NULL, FK → users.user_id, ON DELETE RESTRICT |
| reverses_payment_id | BIGINT | NULL, FK → payments.payment_id, ON DELETE RESTRICT |
| created_at | TIMESTAMPTZ | NOT NULL |

A receipt has no `reverses_payment_id`. A reversal requires one, and it must point at a receipt of the same invoice.

Posting rules:

- The invoice is `posted`.
- After the new receipt, net receipts are less than or equal to `total_amount`.
- After a reversal, reversed amounts for that receipt are less than or equal to the receipt amount.
- Rows are not updated or deleted.

## 15. Posting transactions

Each action below is one database transaction. If any step fails, the whole action rolls back.

| Action | What the transaction writes |
|---|---|
| Verify order | Order status, verifier, finished-goods reservation, audit row. Fails when available stock is short |
| Post purchase receipt | Raw-material movement, balance and average cost, purchase status, audit row |
| Create production run | Run, snapshotted usage plan, lock the BOM on first use, audit row |
| Issue material | Usage actuals and cost, raw-material issue movement, balance, run status, audit row |
| Complete production | Good and damaged quantities, run status, audit row |
| Post production | Finished-goods receipt for `good_quantity`, finished-goods balance and average, run status, audit row |
| Post invoice | Party and tax snapshots, line tax, sequence number, header totals, order status, audit row |
| Post dispatch | Dispatch status, finished-goods issue, reservation and balance, order dispatch status, audit row |
| Receive payment | Receipt row, audit row. Fails when the receipt exceeds the outstanding amount |
| Reverse a posted document | New reversal movement or reversal payment, status fields, restored balance, audit row |

Posted invoice amounts, posted production quantities, movement rows, payment rows, locked BOM lines, and audit rows are not overwritten. A correction is a reversal row or, for stock that has no document reversal, an adjustment movement with a reason.

Editable drafts use `row_version`. An update includes the version the user read and increments it. A mismatched version stops the update.

## 16. Indexes

Primary keys and unique constraints create their own indexes. Additional indexes:

- Every foreign-key column.
- `orders (status, order_date)`.
- `invoices (invoice_number)`, `invoices (invoice_status, invoice_date)`.
- `raw_material_movements (material_id, movement_date)`.
- `finished_goods_movements (product_id, movement_date)`.
- `payments (invoice_id, created_at)`.
- `audit_logs (entity_type, entity_id, created_at)`.
- Partial unique index on `bom_headers (product_id)` where `is_active` is true.
- Partial unique index on `purchases (supplier_id, supplier_invoice_number)` where the supplier invoice number is present.
- Partial unique index on `customers (gstin)` and `suppliers (gstin)` where GSTIN is present.
